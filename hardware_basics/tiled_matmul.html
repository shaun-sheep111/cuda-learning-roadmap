板块二：三个版本对比（对应 day14 的三个 kernel）

① 朴素 matMulNaive

每个线程算 C 的 1 个元素，为此要从全局内存读 A 一整行 + B 一整列（各 K 次）。

相邻线程重复读同样的数据，全局内存被反复读，带宽成为瓶颈。

block 32×32无共享内存

② 基础 tiled 32×32

把 A、B 切成 32×32 的 tile，整块搬进共享内存一次，block 内所有线程复用它。

全局内存读次数降到原来的 1/32。关键靠 __shared__ + __syncthreads()。

TILE_SIZE=32__shared__每线程 1 元素

③ 8×8 register tiling

每个线程改算 8×8=64 个输出元素，把中间结果放进寄存器（最快）。

共享内存里读一次 a/b，就复用在 64 次 FMA 上 —— 算术强度大增，逼近峰值算力。

BM=BN=128BK=8每线程 64 元素acc[8][8] 寄存器

板块三：参数怎么设计才更快

核心矛盾：tile 越大越能复用数据（省带宽），但占用资源越多、能同时跑的 block 越少（occupancy 降）。调参就是在这两者间找平衡。

参数含义调大的好处调大的代价day14 取值
TILE_SIZE共享内存 tile 边长全局内存读更少（复用更多）共享内存/block 占用↑，occupancy↓32（=warp 的整数倍，合并访问好）
BM × BN每个 block 负责的 C 区域数据复用↑，kernel 启动开销摊薄寄存器 + 共享内存压力↑128×128
BKK 方向每次处理的厚度共享内存 tile 小、换入快太小则同步/循环开销占比↑8
每线程输出register tiling 的粒度算术强度↑，访存/计算比改善寄存器用量↑，用超会 spill 变慢8×8=64
block 线程数一个 block 多少线程并行度↑须为 32 倍数，且受寄存器/共享内存限制16×16=256

一句话法则

想让 GPU 算矩阵更快，就是想方设法"少读慢内存、多复用快内存"： 全局内存 → 共享内存 → 寄存器，每往上一层快一个数量级。 分块把数据搬到共享内存复用；register tiling 再把复用推到寄存器层。 参数（TILE/BM/BN/BK/每线程元素）都是在复用收益和occupancy/寄存器预算之间权衡。 最终用 profile（Nsight）实测 occupancy 和 GFLOPS 来定。
